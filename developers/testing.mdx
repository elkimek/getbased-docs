# Testing

getbased uses two test layers:

- **Vitest** wraps the node-side helper fixtures and fast logic checks.
- **Playwright** runs the browser suite against the live app in headless Chrome.

Routstr/Cashu wallet work has an extra release gate because it touches bearer money. Before changing wallet funding, token export/import, seed restore, node deposit/top-up, refunds, or Cashu TS migration code, read [Routstr/Cashu safety](/developers/routstr-cashu-safety).

All first-party tests are authored in TypeScript. Some legacy browser fixtures retain classic-script execution semantics; Playwright executes those through `tests/playwright/browser-script-runner.ts` so they run in the same browser suite as native Playwright specs.

Generated marker catalogs have dedicated drift gates:

```bash
npm run marker-schema:check
npm run marker-terminology:check
```

Use the matching `:build` command after editing authoring modules, then run the focused identity, placement, persistence, or terminology tests relevant to the diff. GitHub Actions owns the exhaustive Chromium and combined-coverage run.

## Test setup and assertions

For CLI-provider and chat-workspace changes, cover the [Companion verification checklist](/developers/cli-agent-providers#verification-checklist) and [chat ownership checks](/developers/chat-internals#change-scoped-verification). Test discovery-only versus installation-authorized credentials separately, unavailable models/targets, canceled uploads, profile switches before the first token, and source-toggle enforcement in tools. Use mocks for routine CI rather than real health records or paid inference. Native OS service installation and OS file dragging require separate platform checks.

Cold-load budgets measure source-mode requests, compressed transfer, and decoded bytes; they are distinct from production chunk budgets. `cold-load-budget.spec.ts` attaches the per-resource inventory for attribution. Record any deliberate feature cost explicitly instead of removing assertions or silently widening the budget. Exhaustive browser and combined-coverage runs belong in GitHub Actions, not an unapproved local full-matrix run.

Install dependencies with Node.js 24 and `npm ci`. `npm test` compiles the app and fixtures before Vitest. Before direct Playwright or Node commands after source edits, run `npm run typescript:build`; keep runtime imports and fixture fetch URLs ending in `.js` or `.mjs`.

Native unit tests use Vitest assertions. For example:

```ts
import { expect, test } from 'vitest';
import { isAllowedProxyUrl } from '../lib/proxy-policy.js';

test('proxy policy rejects loopback destinations', () => {
  expect(isAllowedProxyUrl('https://127.0.0.1/private')).toBe(false);
});
```

Legacy Node fixtures can use `createLegacyAssertions()` from `tests/helpers/legacy-assertions.ts` through its `.js` runtime specifier; the helper returns `assert` and `{ pass, fail }` results. Classic browser fixtures listed in `scripts/classic-browser-fixture-entries.json` keep their assertions inside a typed `runBrowserFixture()` wrapper. The build validates the wrapper and emits its body for the browser-script runner, preserving return values and execution mode. Keep every original assertion when adapting a fixture to TypeScript, and include useful failure details. Prefer native Vitest or Playwright for new tests.

```bash
npm run typecheck:migration
npm run typecheck:migration-tests
npm run typescript:build
npx playwright test tests/playwright/<relevant-spec>.spec.ts
```

## Full CI runner

`./run-tests.sh` runs repository preflight checks, Vitest, the origin guard, and the full Chromium Playwright suite. Use Node.js 24, installed dependencies, and freshly compiled runtime modules. It starts an isolated server on an available port rather than reusing an arbitrary process on port 8000; reuse requires an explicit `REUSE_TEST_SERVER=1`.

Routine local checks should target the changed behavior. The full runner is guarded outside CI because browser profiles and coverage snapshots can write substantial data. An exceptional local full run requires explicit approval for that write volume and this opt-in:

```bash
npm run typescript:build
GETBASED_ALLOW_HIGH_WRITE_TESTS=1 ./run-tests.sh
```

Pull-request CI selects affected tests and runs the relevant gates. Main-branch and manually requested exhaustive CI runs own the full browser/coverage matrix; affected-only results do not constitute full coverage evidence.

## Coverage status

`./run-tests.sh` and the full Playwright command are intentionally guarded outside CI because they run the complete browser matrix and can produce substantial disk writes. Local development should use change-scoped Vitest files and Playwright specs. Run the guarded full matrix only after explicit approval to set `GETBASED_ALLOW_HIGH_WRITE_TESTS=1`; routine exhaustive verification belongs to GitHub Actions.

With CI authorization, `COVERAGE=1 ./run-tests.sh` runs Vitest with V8 coverage, runs the Playwright suite with Chromium JS coverage, then merges `tests/.playwright-coverage/` with `tests/.vitest-coverage/coverage-final.json`. The reporter writes `tests/.coverage.json` and prints separate Playwright, Vitest/Node, and combined global function/byte coverage percentages for app-source JavaScript.

Running `node scripts/playwright-coverage.mjs` directly still falls back to the legacy high-surface Chromium sampler when no Playwright suite shards are present. The full `COVERAGE=1 ./run-tests.sh` path requires suite shards so coverage regressions in the Playwright instrumentation fail clearly.

Combined coverage is enforced by [`scripts/coverage-baseline.json`](https://github.com/elkimek/get-based/blob/main/scripts/coverage-baseline.json): the current global function floor is **89%**, with independent floors for 17 feature groups. `COVERAGE_MIN` can demand a stricter global floor but cannot lower the committed baseline. Missing feature measurements fail the gate.

Runtime coverage measures emitted JavaScript consistently across Node and Chromium. Byte coverage is reported separately and is not line or branch coverage. A separate critical-module Vitest configuration enforces line, statement, function, and branch thresholds for selected safety-sensitive modules; those percentages do not describe the entire app. See [`vitest.critical.config.ts`](https://github.com/elkimek/get-based/blob/main/vitest.critical.config.ts). Keep gate thresholds intact when adding tests or refactoring.

## Accessibility regression scan

`tests/test-a11y-axe.ts` uses the pinned local `axe-core` 4.13 dependency and runs `axe.run()` against the live rendered surfaces. It does not fetch axe from a CDN. Severity policy:

- **critical / serious** → test fails on regression vs baseline
- **moderate / minor** → logged but doesn't block (axe leans opinionated at those tiers)

### Baseline-locked gate

The gate is baseline-relative, and the current critical/serious baseline is zero. Any critical or serious rule at any scanned stop is therefore a regression.

Baseline lives at `tests/.a11y-baseline.json`:

```json
{
  "_axeVersion": "4.13.0",
  "critical": {},
  "serious": {},
  "moderate": {},
  "minor": {}
}
```

The test fails when any critical/serious rule's count **exceeds** the baseline. New rules with non-zero counts ARE a regression (the suite never saw them before). Improvements (current < baseline) pass and emit a hint to refresh the baseline.

`_axeVersion` must match both the local dependency and `PINNED_AXE_VERSION` in the fixture. Update and review all three together when bumping axe because rule changes can appear as regressions.

### Refreshing the baseline

After a wave of fixes that legitimately drops violation counts:

```bash
npm run typescript:build
A11Y_REBASELINE=1 npx playwright test tests/playwright/a11y-axe-browser.spec.ts
```

`tests/playwright/a11y-axe-browser.spec.ts` pipes the env var into the page context before loading the fixture. The test prints a `▶ {...}` JSON line — copy it over the critical/serious/moderate/minor blocks in `tests/.a11y-baseline.json`. Lower counts only after fixing and verifying the corresponding violations. Raising the baseline would accept regressions and requires explicit review.

If the baseline file is missing entirely, the test treats the first run as "establish baseline" and prints the JSON to stdout for paste-back.

Prefer a focused Playwright spec. For a classic browser fixture, compile first and open an isolated demo/test profile at `http://localhost:8000/app`, then use the console:

```js
fetch('/tests/test-ui-flows.js').then(r => r.text()).then(s => Function(s)())
```

Results appear in the console. This works only for compiled classic fixtures in the explicit manifest; Node fixtures such as `test-cycle-improvements.ts` belong in the Node/Vitest harness. Do not use `Function()` to evaluate arbitrary TypeScript or module source.

## Writing new tests

When adding a feature or fixing a bug, cover the behavior in the relevant TypeScript test. If none fits, create a focused `your-feature.test.ts` or Playwright spec. Use source inspection only for contracts that truly depend on source structure; runtime assertions should prove observable behavior.

**What to cover:**

- **Source inspection** — verify the function or pattern exists in the source:
  ```js
  const src = await fetch('js/data.js').then(r => r.text());
  assert('getActiveData exported', src.includes('export function getActiveData'));
  ```

- **DOM state** — check that elements render correctly:
  ```js
  const card = document.querySelector('.context-card[data-key="diet"]');
  assert('diet card rendered', card !== null);
  assert('diet card has edit button', card?.querySelector('.ctx-edit-btn') != null);
  ```

- **Function behavior** — call window-exported functions and check results:
  ```js
  const data = window.getActiveData ? window.getActiveData() : null;
  assert('getActiveData returns dates array', Array.isArray(data?.dates));
  ```

- **CSS rules** — verify styles are applied (use `getComputedStyle` or inspect stylesheets):
  ```js
  const styles = [...document.styleSheets].flatMap(s => {
    try { return [...s.cssRules].map(r => r.cssText); } catch { return []; }
  }).join('\n');
  assert('grid overflow hidden set', styles.includes('min-width: 0'));
  ```

- **Persistence** — in an isolated fixture, save a known record through the feature's API, reload the page, and assert that the same reviewed values are restored. Exercise failure paths separately. Checking that a key might exist, or using an always-true fallback, does not verify persistence.

## Browser automation and manual checks

Playwright can test synthetic drag-and-drop, file uploads, mocked streaming responses, and IndexedDB persistence across reloads. Keep these tests deterministic with isolated storage and controlled provider responses. A fixture runner resetting between files does not prevent a dedicated spec from testing reload persistence.

Manual platform checks remain useful for native OS file dialogs and service installation, real cameras/microphones and hardware, mobile PWA behavior, and live provider compatibility. Paid inference and real wallet funds require deliberate authorization and isolated test data; they are not routine CI requirements.
